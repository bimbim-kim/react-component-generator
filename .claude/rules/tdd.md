# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 예외를 스스로 만들지 말고 그대로 따른다.

**테스트 없이는 프로덕션 코드도 없다.** 실패하는 테스트를 먼저 보지 못했다면 그 코드를 쓰면 안 된다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없는 항목에만 적용한다.

## 적용 기준

### 반드시 적용

- 비즈니스 로직
- API (핸들러, 요청/응답 처리, 에러 매핑)
- 유틸 / 순수 함수
- **버그 수정** (재현하는 실패 테스트 먼저)

### 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

판단이 애매하면 **적용 대상**으로 본다.

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행 없이 실패했다고 가정하지 않는다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 실패한 것은 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패시킨다.

### 2. GREEN — 최소 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. (**YAGNI**)
- 요청되지 않은 옵션, 분기, 추상화를 넣지 않는다.
- **신규 + 기존 테스트 모두 통과**를 확인한다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **테스트는 계속 green이어야 한다.** 매 변경 후 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 새 RED에서 시작한다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.**

## 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. 그 코드를 **삭제**한다.
2. **RED부터 재시작**한다.

- **"참고용"으로 남기는 것도 금지.** 보면서 테스트를 쓰는 순간 테스트는 구현에 종속된다.
- 주석 처리, 별도 파일 보관, 기억에 의존한 재작성 모두 같은 취급이다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 자주 깨진다. 테스트도 30초면 쓴다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓴 것이라 버그를 못 잡는다. 대개 영영 안 쓴다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. TDD가 더 빠르다. |
| "삭제하면 낭비다" | 매몰 비용이다. 검증 안 된 코드를 유지하는 쪽이 더 큰 비용이다. |
| "프로토타입이다" | 프로토타입이 프로덕션이 된다. 버릴 코드라면 삭제 비용도 없다. |

## 체크리스트

- [ ] 테스트를 먼저 썼다
- [ ] 실행해서 "기능 미구현"으로 실패하는 것을 봤다
- [ ] 최소 코드로 통과시켰다
- [ ] 전체 테스트가 green이다
- [ ] 리팩터링 중 새 동작을 넣지 않았다
