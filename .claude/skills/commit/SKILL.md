# Commit

변경사항을 읽고, 의미 있는 단위로 쪼개고, 컨벤션에 맞는 한국어 메시지를 작성해 승인 질문 없이 바로 커밋한다. 커밋 요청 자체가 실행 승인이다.

## 원칙

- 커밋 전에 사용자에게 계획을 확인하거나 승인을 묻지 않는다. 분류와 메시지는 스스로 판단해 확정하고 바로 실행한다.
- 판단이 애매한 경우에도 질문하지 말고 보수적인 쪽(더 작은 단위, 제외)으로 정한 뒤 결과 보고에 그 판단을 적는다.
- `git push`, `--amend`, `--no-verify`, `rebase`, `reset --hard`는 사용자가 명시적으로 요청할 때만 쓴다.
- 비밀 정보가 담길 수 있는 파일(`.env`, `*.pem`, `*.key`, 자격 증명 JSON 등)은 커밋 대상에서 제외하고 사용자에게 알린다.
- 메시지는 diff에서 실제로 확인한 내용만 쓴다. 추측으로 이유를 지어내지 않는다.

## 절차

### 1. 상태 확인

```bash
git rev-parse --is-inside-work-tree   # 저장소가 아니면 중단한다
git status --short
git diff --stat
git diff --cached --stat
git log --oneline -10                 # 기존 메시지 스타일 참고
```

- 저장소가 아니면 중단하고 `git init`이 필요하다고 알린다. 저장소를 새로 만드는 일은 요청 범위 밖이므로 임의로 실행하지 않는다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- 이미 스테이징된 변경이 있으면 기본적으로 그것만 커밋 대상으로 본다. 인자에 `--all`이 있거나 스테이징된 것이 없으면 전체 작업 트리를 대상으로 한다.
- 추적되지 않은 파일(`??`)은 내용을 확인한 뒤 포함 여부를 판단한다. 빌드 산출물, 로그, 임시 파일은 제외를 제안한다.

### 2. 변경사항 분석

```bash
git diff            # 스테이징 안 된 변경
git diff --cached   # 스테이징된 변경
```

파일별로 무엇이 왜 바뀌었는지 파악한다. diff가 크면 `git diff -- <path>`로 나눠 읽는다. 새 파일은 Read로 내용을 확인한다.

### 3. 논리적 단위로 분류

하나의 커밋은 하나의 의도만 담는다. 다음 기준으로 묶는다.

- 같은 기능이나 같은 버그 수정에 속하는 변경은 파일이 달라도 한 커밋으로 묶는다. 구현과 그 테스트는 함께 둔다.
- 동작 변경과 무관한 정리(리네이밍, 포맷, 구조 개선)는 기능 커밋과 분리한다.
- 의존성, 설정, 빌드 스크립트 변경은 별도 커밋으로 분리한다.
- 한 파일 안에 서로 다른 의도의 변경이 섞여 있으면 파일 단위로 가장 비중이 큰 의도의 커밋에 넣고, 결과 보고에 그 사실을 적는다. `git add -p` 같은 대화형 명령은 쓰지 않는다.
- 단위가 하나뿐이면 굳이 쪼개지 않는다.

### 4. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 쓰는 경우 |
|------|-----------|
| feat | 사용자가 체감하는 기능 추가나 변경 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 코드 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서, 스타일 등 그 외 |

규칙:

- 요약은 한국어, 50자 이내, 마침표 없이, 명사형이나 "~추가", "~수정"처럼 끝낸다. 예: `feat: 프롬프트 예시 클릭 시 입력창 자동 채우기 추가`
- 본문은 변경 이유나 영향이 요약만으로 드러나지 않을 때만 쓴다. 한 줄 72자 안팎으로 줄바꿈하고, 무엇을 왜 바꿨는지 쓴다.
- 저장소의 기존 로그가 다른 컨벤션을 쓰면 이 스킬의 형식(`type: 요약`)을 따르되, 결과 보고에 차이를 한 줄로 알린다.
- 시스템이 지정한 커밋 attribution 줄(예: `Co-Authored-By`)이 있으면 메시지 끝에 붙인다.

### 5. 커밋 계획 공지

커밋 계획을 다음 형태로 짧게 알린 뒤, 응답을 기다리지 않고 곧바로 6단계를 실행한다.

```
커밋 1/2
  파일: src/App.tsx, src/App.css
  메시지:
    feat: 레트로 데스크톱 스타일로 메인 레이아웃 변경

커밋 2/2
  파일: index.html
  메시지:
    chore: Galmuri, IBM Plex 웹폰트 추가

제외: .env (비밀 정보 포함 가능)
```

- 이 공지는 승인 요청이 아니라 진행 상황 안내다. 질문형 문장("진행할까요?")을 붙이지 않는다.
- 사용자가 중간에 끼어들어 중단이나 수정을 요청하면 그때 멈추고 따른다.

### 6. 커밋 실행

커밋마다 해당 파일만 스테이징하고 커밋한다. 메시지는 heredoc으로 전달해 줄바꿈과 따옴표를 보존한다.

```bash
git add -- <파일들>
git commit -F - <<'EOF'
feat: 요약

본문
EOF
```

- 시작 시점에 이미 스테이징된 파일이 다른 커밋 단위에 속하면, 먼저 `git restore --staged -- <파일>`로 내린 뒤 단위별로 다시 스테이징한다. 이 조정도 5단계 공지에 포함한다.
- pre-commit 훅이 실패하면 우회하지 말고 오류 내용을 보여준다. 훅이 지적한 문제가 이번 변경 범위 안에서 명확히 고쳐지면 고친 뒤 새 커밋으로 다시 시도하고, 범위 밖이거나 판단이 필요하면 중단하고 보고한다.

### 7. 결과 보고

```bash
git log --oneline -<커밋 수>
git status --short
```

만든 커밋의 해시와 메시지, 남은 변경사항(제외한 파일 포함)을 짧게 알린다. push는 제안만 하고 실행하지 않는다.
